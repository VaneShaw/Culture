# 视频模块优化方案

## 文档说明

- 目的：将当前视频模块的体验优化点整理为可执行的阶段性方案，覆盖首帧、封面、预热、切换状态机、分类切换降载、全屏无缝、收藏流平滑、分享链路修正以及日志验证。
- 范围：主要涉及 `YTVPlayerSessionManager`、`YTVVideoPreloadManager`、`YTVShortVideoFeedViewController`、`YTVShortVideoCell`、`YTVShortVideoFeedViewModel`、`YTVVideoPRDShareHelper`、`YTVFeedFullscreenViewController` 等模块。
- 目标：减少黑屏、提升首帧稳定性、优化回滑体验、降低分类切换损耗、保证全屏与列表播放连续性，并修正收藏流与分享链路行为。

---

## Phase 1：首帧与封面链路

### 目标

- 将“item 可播放”和“首帧已经真正渲染出来”拆成两个阶段。
- 封面不再在 `ReadyToPlay` 时提前消失，而是在首帧真正到达后再隐藏。
- 避免快速连滑时旧播放回调污染当前播放状态。

### `YTVPlayerSessionManager.h`

- 增加播放状态回调接口，建议使用 block 或 delegate。
- 至少暴露以下事件：
  - `itemReady`
  - `firstFrameRendered`
  - `playFailed`
- 增加当前播放 `token` / `requestId`，用于过滤旧播放请求回调。

### `YTVPlayerSessionManager.m`

- 在 `replacePlaybackWithURL:preferredPrewarmedPlayerItem:completion:` 中，不再把 `completion` 的含义定义为“可以揭封面”。
- 保留 `status == AVPlayerItemStatusReadyToPlay` 作为“item 可播放”信号。
- 额外增加“首帧到达”监听。
- 首帧监听第一版建议优先使用：
  - `AVPlayerLayer.readyForDisplay`
- 后续如需更精细控制，可升级为：
  - `AVPlayerItemVideoOutput` 的可出帧状态
- `play` 时除了处理 `AVAudioSession`，还要把当前 `requestId` 带进回调校验。
- `clearPlayback` 时必须完整清理：
  - `item observer`
  - `first frame observer`
  - `pending callback`

### `YTVShortVideoFeedViewController.m`

- 增加字段：
  - `ytv_pendingBindIndex`
  - `ytv_isSwitchingPlayback`
- 调整 `ytv_applyPlaybackForCurrentIndexIfPossible`：
  - 先让当前 cell 显示封面
  - `attach player`
  - 调用 session 切源
  - `itemReady` 时不隐藏封面
  - `firstFrameRendered` 时才隐藏封面
  - `playFailed` 时显示失败态，或者至少保留封面
- 当前 completion 中的 `ytv_setCoverHidden:YES` 逻辑要移除。
- completion 最多只做“确认当前绑定仍有效”。
- 如果当前 URL 与 `player.currentItem` 相同：
  - 不重新切源
  - 直接 re-attach 到当前 cell
  - 如果已经首帧 ready，立即隐藏封面
- 用户快速连滑时，旧 completion 回来后必须校验：
  - `currentPlayIndex == bindIdx`
  - `ytv_pendingBindIndex == bindIdx`

### `YTVShortVideoCell.h`

- 增加方法声明：
  - `- ytv_showCoverImmediately`
  - `- ytv_hideCoverAfterFirstFrameAnimated:(BOOL)animated`
  - `- ytv_showPlaybackFailureState`
  - `- ytv_clearPlaybackFailureState`

### `YTVShortVideoCell.m`

- 将现有 `ytv_setCoverHidden:animated:` 包装成更语义化的方法。
- `prepareForReuse` 中除重置 cover 外，也重置 failure state。
- `configureWithItem:` 之后默认保持 cover 显示，直到 VC 收到首帧通知。
- 如果暂时不做复杂失败 UI，`ytv_showPlaybackFailureState` 第一版可仅保留 cover，不额外增加控件。

## Phase 2：真预热

### 目标

- 将当前“只提前创建 `AVPlayerItem`”升级为“真正触发资源准备”。
- 提升下一条、回滑条目的可播命中率。
- 控制预热窗口与带宽消耗，避免过度预热。

### `YTVVideoPreloadManager.h`

- 将当前只暴露 `AVPlayerItem` 的接口，升级为“预热条目”接口。
- 新增内部模型或字典结构，字段建议包含：
  - `videoId`
  - `playURL`
  - `asset`
  - `playerItem`
  - `state`
  - `lastAccess`
- 对外接口建议增加：
  - `- warmAroundDisplayIndex:items:`
  - `- preparedPlayerItemForVideoId:playURL:`
  - `- markPlaybackProtectedVideoId:`
  - `- trimWarmPoolPreservingCurrentWindow`

### `YTVVideoPreloadManager.m`

- 当前逻辑只是在创建 `AVPlayerItem`，应改为真正触发资源准备流程。
- 增加状态枚举：
  - `Idle`
  - `Preparing`
  - `Prepared`
  - `Failed`
- HLS / MP4 第一版通用方案：
  - `AVURLAsset *asset = [AVURLAsset URLAssetWithURL:options:]`
  - `loadValuesAsynchronouslyForKeys:@[@"playable", @"tracks"]`
  - 校验 key status
  - 成功后再创建 `AVPlayerItem`
  - 给 `item` 设置 `preferredForwardBufferDuration`
  - 状态改为 `Prepared`
- 预热窗口建议调整为固定小窗口：
  - `displayIndex - 1`
  - `displayIndex + 1`
  - `displayIndex + 2`
- 当前的 `+3` 可先去掉，避免浪费带宽。
- warm 池淘汰时优先保留：
  - 当前播放 `videoId`
  - 上一条
  - 后两条
- `takePrewarmedItemForVideoId` 改成只返回 `Prepared` 状态对象里的 `item`。
- 回滑 touch 逻辑保留，但改成更新 `lastAccess`。

### `YTVShortVideoFeedViewController.m`

- `ytv_warmAroundProvisionalDisplayIndex:` 继续保留，但只负责预测下一页并触发预热。
- `ytv_applyPlaybackForCurrentIndexIfPossible` 中拿预热 item 时，只取 prepared item。
- `ytv_reloadUIForViewModelState` 在 `Ready` 状态下的启动顺序调整为：
  - 先 warm 当前附近
  - 再尝试播放当前页
- 避免刚进入页面时还未 warm 就立刻冷切源。

## Phase 3：播放切换状态机

### 目标

- 将当前切换播放的逻辑显式拆成状态机流程。
- 降低 `ytv_applyPlaybackForCurrentIndexIfPossible` 的复杂度。
- 保证快速滑动时播放绑定关系始终正确。

### `YTVShortVideoFeedViewController.m`

- 改造 `ytv_syncPlayIndexFromContentOffset`：
  - 如果新 `index` 和旧 `index` 相同，只做预热与补货
  - 如果不同，先记录 `oldPlayIndex`
  - 再设置 `pendingBindIndex = idx`
  - 最后触发切源
- 改 `ytv_applyPlaybackForCurrentIndexIfPossible` 为严格流程：
  - 校验 `currentPlayIndex` 合法
  - 取 item
  - 当前 cell 显示 cover
  - attach player
  - 如果 `currentItem URL` 已相同且已 ready，则直接恢复
  - 否则执行切源
  - 回调回来后再次校验 `pendingBindIndex`
- 建议新增 helper：
  - `ytv_currentCellForPlaybackIndex`
  - `ytv_prepareCellForSwitchingPlaybackAtIndex`
  - `ytv_finishFirstFrameAtIndex`
  - `ytv_failPlaybackAtIndex:error:`
- 通过 helper 将播放切换逻辑拆散，避免方法内部堆积过多分支。

## Phase 4：分类切换降载

### 目标

- 横向切分类时不再把当前播放会话完全清空。
- 保留当前 item 与近邻预热项，提升分类切回时的恢复速度。
- 避免分类切回时像重新进入新页面一样重新冷启动。

### `YTVShortVideoFeedViewController.m`

- 修改 `ytv_deactivateCategoryFeed`：
  - 保留 `pause`
  - 保留 `detachPlayerFromVisibleCells`
  - 去掉无条件 `clearPlayback`
  - 去掉无条件 `invalidateAllWarmItems`
- 新增轻量降载方法，例如：
  - `ytv_reduceInactiveCategoryResources`
- 该方法只做：
  - 保留当前 item
  - 保留近邻 warm items
  - 淘汰远端 warm items
- 修改 `ytv_activateCategoryFeed`：
  - 如果 `player` 上仍是当前 URL，直接 attach
  - 否则再走切源

### `VideoTabViewController.m`

- 当前结构可保留，不需要大改。
- 只需保证：
  - 当前激活 feed 调 `activate`
  - 其他 feed 调 `deactivate`
- 不销毁并重建 feed VC。

## Phase 5：全屏无缝切换

### 目标

- 从 Feed 进入全屏时，继续复用同一个 `AVPlayer`。
- 进入与退出全屏不重新 replace item，不中断当前播放会话。
- 避免因 `viewWillDisappear` 默认 pause 导致全屏黑一下或重新起播。

### `YTVShortVideoFeedViewController.m`

- 修改 `viewWillDisappear`：
  - 不再无条件 `pause`
- 增加标志位：
  - `ytv_presentingFullscreen`
- 点击全屏前先置：
  - `ytv_presentingFullscreen = YES`
- `viewWillDisappear` 中判断：
  - 如果是 going fullscreen，不 pause
  - 如果是切 Tab / push 文本页 / 离开页面，再 pause
- `viewDidAppear` 中如果是从全屏回来：
  - 重新 attach 当前 cell
  - 不 replace item
  - 只在必要时 resume

### `YTVFeedFullscreenViewController.m`

- 继续共享同一个 `AVPlayer`。
- `viewDidAppear` 中的 `play` 可保留，但前提是 feed 页没有提前 pause。
- 关闭全屏时：
  - 不清理 player
  - 不 replace item
- 全屏页仅负责显示层切换，不承担播放会话切换职责。

---

## Phase 6：收藏流取消收藏平滑化

### 目标

- 在收藏流中取消收藏时，不立刻把当前视频从列表删掉。
- 避免用户正在看的视频突然消失、列表突跳、重新 bind 播放。
- 将删除动作延迟到用户真正离开该条后再清理。

### `YTVVideoFeedItem.h`

- 增加一个仅客户端会话内使用的临时字段：
  - `ytv_pendingRemovalAfterLeave`
- 该字段不进入持久化快照。

### `YTVShortVideoFeedViewModel.m`

- 修改收藏流取消收藏成功后的处理：
  - 不立刻 `removeObjectAtIndex`
  - 改为 `item.ytv_pendingRemovalAfterLeave = YES`
- 新增方法：
  - `- ytv_cleanupPendingRemovalExcludingVideoId:(NSString *)currentVideoId`
- 该方法在用户离开当前播放项后调用，删除所有：
  - `pendingRemovalAfterLeave == YES`
  - 且 `videoId != currentVideoId`
- 删除后同步更新 snapshot。

### `YTVShortVideoFeedViewController.m`

- 在 `ytv_syncPlayIndexFromContentOffset` 切到新 index 后：
  - 调用一次 `cleanupPendingRemovalExcludingVideoId:newCurrentVideoId`
- 如果 cleanup 导致数量变化：
  - 再 `reloadData`
  - 保持当前 index 对应的视频稳定
- 修改当前取消收藏成功后的刷新逻辑：
  - 不再立刻 `reload + setContentOffset + applyPlayback`
  - 只有当当前列表真的空了，才 `pop`

## Phase 7：分享链路修正

### 目标

- 分享与复制链接应以“当前视频”作为主对象，而不是固定下载页。
- 优先使用服务端下发的 `shareURL`，没有时再回退到客户端拼接链接。
- 统一分享和复制链接逻辑，避免链路分裂。

### `YTVVideoPRDShareHelper.h`

- 新增接口：
  - `+ ytv_presentShareForItem:fromViewController:sourceView:`
  - `+ ytv_copyShareLinkForItem:`
  - `+ ytv_shareURLStringForItem:`

### `YTVVideoPRDShareHelper.m`

- 修改当前只分享下载页的逻辑。
- 生成分享链接顺序改为：
  - 如果 `item.shareURL` 有值，直接使用
  - 否则回退到 `https://shiyi.yitong.com/app/video?id={video_id}&from=share`
- `UIActivityViewController` 的 items 改成：
  - 当前视频标题或文案
  - 当前视频的 share URL
- 复制链接时，改为复制当前视频链接。
- 当前固定 download URL 仅作为 fallback，不再作为主链路。

### `YTVShortVideoFeedViewController.m`

- 修改 `ytv_onShareChromeTap`
- 修改 `ytv_onCopyDownloadLinkChromeTap`
- 两处均改为读取当前 `YTVVideoFeedItem`

## Phase 8：日志与验证

### 目标

- 为播放、预热、切换、全屏、分页等关键路径补 debug log。
- 方便定位“是切源慢、首帧慢、预热没命中，还是错误回调串了”。
- 为每个阶段改动后的手测和回归提供观测依据。

### `YTVPlayerSessionManager.m`

- 增加 debug log：
  - `replace start`
  - `item ready`
  - `first frame rendered`
  - `play failed`
- 建议日志打印字段：
  - `videoId`
  - `url`
  - `elapsed ms`

### `YTVVideoPreloadManager.m`

- 增加 debug log：
  - `warm enqueue`
  - `warm prepared`
  - `warm failed`
  - `warm hit`
  - `warm evict`

### `YTVShortVideoFeedViewController.m`

- 增加 debug log：
  - `currentPlayIndex change`
  - `next page prefetch trigger`
  - `deep link focus`
  - `fullscreen enter / exit`

## 建议提交顺序

1. `PlayerSessionManager + Cell + FeedVC` 首帧链路
2. `PreloadManager + FeedVC` 真预热
3. `FeedVC` 分类降载 + 全屏无缝
4. `FeedViewModel + FeedVC` 收藏流平滑
5. `ShareHelper + FeedVC` 分享修正
6. Debug 日志与回归测试

---

## 每一步完成后的手测项

- 冷启动进入视频页
- 连续下刷 10 条
- 上下回滑
- 左右切分类再切回
- 点全屏再退出
- 收藏流取消收藏
- 分享当前视频

---

## 实施建议补充

- Phase 1 和 Phase 2 优先级最高，它们直接决定用户能否明显感知到“黑屏变少、首帧更稳、回滑更快”。
- Phase 3 适合作为状态清理与结构收口阶段，避免后续逻辑继续叠加在单个大方法中。
- Phase 4 和 Phase 5 主要解决“切分类 / 进全屏像重新起播”的割裂感，建议联动实施。
- Phase 6 和 Phase 7 更偏交互一致性与产品完整度，可在主播放链路稳定后再合入。
- Phase 8 应贯穿全程，至少在开发分支中保留足够日志，方便回归与问题复现。
